# Feature Specification: LIFF 登入取得後端 JWT 授權

**Feature Branch**: `001-liff-jwt-login`

**Created**: 2026-08-04

**Status**: Draft

**Input**: User description: "我想在liff登入後，向後端取得jwt，憑此jwt可以跟後端做出一些進一步的互動"

## Clarifications

### Session 2026-08-04

- Q: 客戶換發到的授權憑證，應該設定多長的有效期限？ → A: 30 分鐘
- Q: 當授權換發失敗的原因是「後端服務無回應或發生錯誤」而非「LINE 身分驗證失敗」時，系統應該怎麼呈現？ → A: 區分兩種錯誤文案，服務錯誤額外提供「重試」按鈕
- Q: 客戶的 LINE 帳號被解除綁定後，尚未過期的授權憑證應該立即失效，還是可沿用至自然過期？ → A: 可沿用至自然過期（最長 30 分鐘），不做即時撤銷檢查——此情境發生機率低，可接受此風險窗口
- Q: 當客戶尚未登入 LINE、無法完成授權換發時，換發機制本身應該自動導向 LINE 登入頁，還是應該把「尚未登入」狀態交給各頁面自行決定要不要顯示登入按鈕？ → A: 換發機制本身不強制導頁；「尚未登入」狀態由各頁面自行決定 UI 呈現方式，例如 `OrderView.vue` 顯示「登入」按鈕，由客戶主動點擊後才觸發 LINE 登入導轉（比照該頁現有手動綁定按鈕的模式），而非在頁面載入當下就強制把客戶導離頁面

## User Scenarios & Testing *(mandatory)*

### User Story 1 - LIFF 登入後換發後端授權憑證 (Priority: P1)

客戶透過 LINE LIFF 開啟本站頁面且已登入 LINE 帳號時，前端會將其 LINE 身分憑證換發成後端核發的授權憑證（JWT）。之後前端對後端受保護 API 的請求都會附上此授權憑證，讓後端能辨識出請求是由哪一位客戶送出，客戶不需要額外輸入帳號密碼。

**Why this priority**: 這是整個功能的核心與前提——沒有換發授權憑證的機制，任何「進一步的互動」都無從談起，必須最先完成且可獨立驗證。

**Independent Test**: 在已完成 LINE 綁定的客戶帳號下，透過 LIFF 內建瀏覽器開啟頁面並確認已登入 LINE，驗證前端能取得一組有效期內的授權憑證，且能用其對受保護端點成功發出請求。

**Acceptance Scenarios**:

1. **Given** 客戶已在 LIFF 內登入 LINE 且該 LINE 身分已與後端客戶資料綁定，**When** 客戶開啟本站的 LIFF 頁面，**Then** 前端自動取得後端核發的授權憑證，客戶不會被要求採取任何額外的登入動作。
2. **Given** 客戶尚未登入 LINE，**When** 客戶開啟 LIFF 頁面，**Then** 系統不會自動把客戶導離頁面去登入；頁面本身依其既有 UI（例如登入/綁定按鈕）呈現「尚未登入」狀態，客戶主動點擊後才觸發 LINE 登入流程，登入完成後導回原頁面並自動接續完成授權憑證換發。
3. **Given** 客戶持有一組有效的授權憑證，**When** 前端對後端受保護 API 發出請求，**Then** 該請求會挾帶此授權憑證，後端能辨識出對應的客戶身分。

---

### User Story 2 - 授權狀態在有效期內延續，避免重複登入 (Priority: P2)

客戶在授權憑證尚未過期前重新開啟 LIFF 頁面（例如重新整理頁面、關閉又重新開啟 LINE 對話），系統應沿用既有授權狀態，不需要重新跑一次 LINE 登入導轉流程。

**Why this priority**: 直接影響使用體驗的流暢度，但不是換發機制本身的前提，可在 P1 完成後疊加。

**Independent Test**: 換發授權憑證後，於有效期內重新載入頁面，確認前端未觸發 LINE 登入導轉、並沿用既有授權憑證（或在背景無感重新換發）完成後續請求。

**Acceptance Scenarios**:

1. **Given** 客戶先前已成功換發一組尚未過期的授權憑證，**When** 客戶重新載入 LIFF 頁面，**Then** 系統沿用既有授權憑證或在背景無感重新換發，客戶不會看到登入畫面。
2. **Given** 授權憑證已過期，**When** 客戶重新載入頁面，**Then** 系統以客戶目前的 LINE 登入狀態自動重新換發一組新的授權憑證，同樣不需客戶採取額外動作（只要其 LINE 登入本身仍然有效）。

---

### User Story 3 - 授權失敗時的錯誤處理 (Priority: P3)

當授權憑證換發失敗時（例如 LINE 身分驗證失敗），系統需要給客戶清楚、友善的提示，而不是讓頁面卡住或顯示技術性錯誤。

**Why this priority**: 錯誤處理是完善體驗必要的一環，但依賴 P1 的換發流程先存在才有意義，優先權低於核心流程。

**Independent Test**: 模擬換發失敗的情境（例如帶入失效的 LINE ID Token），確認前端顯示對應的錯誤提示文案，而非空白畫面或未處理的例外。

**Acceptance Scenarios**:

1. **Given** 客戶的 LINE 身分驗證失敗，**When** 前端嘗試換發授權憑證，**Then** 系統顯示清楚的身分類錯誤訊息，說明目前無法完成登入。
2. **Given** 客戶的 LINE 身分尚未透過既有訂單綁定流程綁定至任何客戶資料，**When** 前端嘗試換發授權憑證，**Then** 系統拒絕換發，並顯示提示引導客戶先透過訂單分享連結完成綁定。
3. **Given** 換發請求因後端無回應、逾時或伺服器錯誤而失敗，**When** 前端嘗試換發授權憑證，**Then** 系統顯示「服務暫時無法使用」類訊息並提供「重試」按鈕，不會誤導客戶以為是自己身分的問題。

---

### Edge Cases

- LIFF SDK 初始化失敗（`liff.init` 失敗）時，已決議：視為服務類錯誤處理，比照 FR-006 服務類錯誤的呈現方式（顯示「服務暫時無法使用」文案並提供重試按鈕），不歸類為身分類錯誤（見 FR-006）。
- 客戶在換發流程進行中關閉 LIFF 視窗或切換頁面時，已決議：無需額外處理，未完成的換發請求隨頁面卸載由瀏覽器原生中止即可，不需要專屬的取消/清理邏輯。
- 客戶的 LINE 身分憑證已過期或格式不正確時，後端如何回應、前端如何呈現？
- 客戶已換發授權憑證後，若在同一裝置以一般瀏覽器（非 LIFF 容器）直接造訪本站其他頁面，此授權憑證是否仍套用？
- 客戶的 LINE 綁定於授權憑證效期內被解除時，該憑證可繼續使用至自然過期（最長 30 分鐘），系統不做即時撤銷檢查（見 FR-009）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統必須能將客戶在 LIFF 內已驗證的 LINE 身分憑證，換發為一組後端核發、具備效期的授權憑證。
- **FR-002**: 客戶尚未登入 LINE 時，系統不得自動將客戶導離目前頁面去強制登入；換發機制只需將「尚未登入」狀態提供給頁面，實際是否顯示登入按鈕、以及登入流程何時被觸發，由各頁面自行決定 UI 呈現（例如比照 `OrderView.vue` 現有的手動綁定按鈕模式）。客戶主動觸發登入後，登入完成需能自動接續換發流程，不需要客戶手動重新觸發第二次。
- **FR-003**: 系統必須將換發成功的授權憑證用於後續對後端受保護端點的請求，讓後端可辨識請求對應的客戶身分。
- **FR-004**: 系統必須將已換發的授權憑證保存在瀏覽器的工作階段儲存中（同一分頁/工作階段內重新整理頁面仍可沿用，不需重新換發；工作階段結束（如分頁關閉）後即視為失效，下次開啟需重新換發），避免同一次瀏覽過程中重複觸發不必要的換發或登入導轉。
- **FR-005**: 授權憑證的有效期為 30 分鐘；系統必須在授權憑證過期後，於下一次需要呼叫受保護端點時自動嘗試重新換發，且此重新換發對客戶而言應是無感的（只要其 LINE 登入狀態仍然有效）。
- **FR-006**: 換發失敗時，系統必須依失敗原因區分兩種呈現方式，不得讓畫面卡在載入狀態或顯示未經處理的技術錯誤：
  - 客戶身分原因（LINE 身分驗證失敗、憑證格式錯誤、未滿足 FR-007 的綁定前提等）→ 顯示對應的身分類錯誤訊息，引導客戶重新登入或補綁定。
  - 服務暫時無法使用（後端無回應、逾時、伺服器錯誤、LIFF SDK 初始化失敗等網路/服務類原因）→ 顯示「服務暫時無法使用，請稍後再試」類訊息，並提供「重試」按鈕讓客戶重新觸發換發，不誤導客戶以為是自己身分的問題。
- **FR-007**: 換發授權憑證要求該 LINE 身分必須已透過現有「訂單綁定」流程（`POST /api/public/orders/bind`）綁定至客戶資料；系統必須能辨識此前提是否成立，未成立時必須拒絕換發並提示客戶先完成綁定，不會為未綁定的 LINE 身分建立或推論客戶身分。
- **FR-008**: 系統必須將換發流程設計為與特定頁面無關的共用能力：任何現有或未來新增的 LIFF 頁面（不僅限於 `OrderView.vue`）都能觸發並沿用同一套換發邏輯，不需要各頁面各自重新實作一遍。
- **FR-009**: 系統不需要在授權憑證效期內即時檢查客戶的 LINE 綁定關係是否仍然成立；客戶解除綁定後，既有未過期的授權憑證可繼續使用至其效期（最長 30 分鐘）自然屆滿，此為業務單位評估後可接受的風險窗口，不需額外的即時撤銷機制。

### Key Entities

- **客戶授權憑證（Customer Session）**：代表客戶登入後的授權狀態，包含效期與所對應的客戶身分；由後端核發，前端持有並於請求時附帶。
- **LINE 身分憑證（LINE Identity Credential）**：客戶在 LIFF 內完成 LINE 登入後取得，作為換發後端授權憑證的憑證來源。
- **客戶（Customer）**：與 LINE 身分綁定、且為授權憑證所代表的身分主體。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 已完成 LINE 綁定的客戶於 LIFF 內開啟頁面後，可在 3 秒內於背景完成授權換發，無需任何手動操作。
- **SC-002**: 授權憑證換發失敗時，100% 的失敗情境都會呈現客戶看得懂的錯誤訊息，不會出現空白畫面或未處理例外。
- **SC-003**: 在授權憑證有效期（30 分鐘）內，客戶重新整理頁面或重新進入 LIFF 頁面時，不被要求重新跑一次 LINE 登入導轉的比例達到 100%（即無感延續授權狀態）。
- **SC-004**: 客戶因授權憑證換發失敗而需要重新嘗試，整體流程可在 2 次操作以內（例如「重新開啟頁面」加上最多 1 次重試）完成，不需要客戶自行排除障礙。

## Assumptions

- 本功能沿用既有 `src/views/OrderView.vue` 已導入的 LIFF SDK 與既有的 LINE 登入流程（初始化、登入導轉、取得 LINE 身分憑證），不另外導入其他登入機制。
- 換發機制本身不擁有、也不決定「尚未登入」狀態下的頁面 UI；是否顯示登入按鈕、按鈕文案、與頁面其他既有目標（例如 `OrderView.vue` 的訂單綁定）如何並存，都由各頁面自行設計，換發機制只負責在客戶主動完成登入後接續完成授權憑證換發（詳見 FR-002）。
- 「進一步的互動」目前沒有具體、已知的受保護功能清單；本功能範圍僅止於「取得並維護一組可用的授權憑證」這項基礎能力，實際會用到此授權憑證的畫面/功能將於後續各自的規格另行定義，不在本規格範圍內。
- 換發授權憑證所需的後端端點目前尚未存在（現有後端公開 API 僅有訂單查詢/綁定端點，以及後台帳號密碼登入端點，沒有「以 LINE 身分換發客戶授權憑證」的端點）；此端點的存在與可用性屬於後端另一個 repo 的相依工作，不在本前端 repo 的實作範圍內，但本規格描述前端對其的預期行為。
- 授權憑證採瀏覽器工作階段儲存（同一分頁/工作階段內持續有效，工作階段結束即失效，詳見 FR-004）；實際請求附帶方式（例如放在哪個 request header）由前端實作階段決定，本規格不預先指定技術細節。
- 換發授權憑證的能力設計為與頁面無關的共用機制（見 FR-008），但實作階段的抽出時機（例如是否現在就抽成共用 composable，或先在 `OrderView.vue` 內完成再抽取）由實作規劃另行決定。
